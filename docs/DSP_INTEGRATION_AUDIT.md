# DSP integration audit — Android Music Player

Date: 2026-10-25

## Decision

Do **not** replace the current just_audio playback path in this patch. Keep the existing player as the production backend until a separate native-DSP backend passes playback and device regression tests. This preserves library scanning, current-track state, seeking, and the existing Now Playing UI.

## Findings from the current repository

- pubspec.yaml currently uses just_audio ^0.10.4; it does not depend on miniaudio_player.
- lib/main.dart sends configure messages over android_music_player/audio_effects and expects an Android audio session ID.
- The Android bridge is generated by .github/workflows/build-apk.yml during CI. It creates Android Equalizer, BassBoost, and Virtualizer effects for the active session.
- Those Android effects are device/vendor implementations. An effect object can be unavailable, silently bypassed, or sound different across devices.
- Virtualizer is not the same as a software stereo widener. Therefore the current bridge cannot guarantee a consistent, embedded stereo-width effect on every device.
- The current equalizer UI exposes seven sliders, while the platform equalizer may expose a different number of bands. The bridge maps the seven UI controls to native band frequencies; this is an approximation, not a portable seven-band DSP filter chain.
- The current README describes some playback functionality as future work, although lib/main.dart now contains local file selection, folder scanning, and playback logic. Keep documentation aligned as the project evolves.

## Additional runtime defects found during the second pass

The production Dart code had several controls that changed their UI state without consistently applying the new values to the native engine:

- The audio effects were applied immediately after setFilePath and before play(). If just_audio had not created/exposed its Android audio session yet, _applyAudioEffects returned early and no retry was guaranteed.
- Bass intensity and surround width sliders only called setState; dragging them did not send the new strengths to the native effects.
- The dropdown preset in _presetChips updated the seven band values without applying the preset to the native equalizer.
- Reverb, Chorus, Flanger and Delay dials are display-only controls. They are not backed by native DSP and must not be presented as functional effects.

The audit branch now listens to just_audio's Android audio-session-ID stream and reapplies settings when a non-null session appears (without awaiting the long-lived play() future), reapplies Bass Boost and Virtualizer values when their sliders move, applies the dropdown preset, and updates the status note to distinguish native controls from visual-only dials. This is a targeted bug fix, not proof of audible DSP output; the native device test is still required.

## Evaluation: miniaudio_player

The package page currently advertises version 2.1.0, MIT licensing for the package, native miniaudio playback, a 10-band EQ, bass-boost preset, limiter, and a stereo spatializer. It uses Dart Native Assets / FFI and has a substantially different playback API from just_audio.

**Why it is not added to production dependencies in this audit patch:**

1. Version 2.1.0 was published only days before this audit; package maturity and device coverage are not established by the listing alone.
2. Adopting it means replacing the playback backend, not just adding an EQ helper. The current AudioPlayer, state streams, seeking, source selection, and session-based Android effects all need an explicit adapter/migration.
3. Its published third-party acknowledgements include a Helix AAC decoder under the RealNetworks Public Source License (RPSL). Review the bundled component's terms for the intended distribution/commercial use before shipping.
4. The project must prove Android release builds and runtime behavior on actual devices before changing the default backend.

References:
- https://pub.dev/packages/miniaudio_player
- https://docs.flutter.dev/packages-and-plugins/using-packages

## Recommended implementation sequence

### Phase A — keep the existing backend working

- Do not remove or replace just_audio.
- Verify the Android MethodChannel is generated by CI and that an actual audio session ID is available after loading a track.
- Make effect availability explicit in the UI/logs; do not report an effect as active if the platform returns no usable effect.
- Re-apply settings after a new track/session is created and release native effect instances when their session is replaced.
- Validate EQ band range and effect strengths against each Android effect's advertised ranges.
- Treat Android Virtualizer as best-effort vendor processing, not as portable stereo widening.

### Phase B — isolated miniaudio_player compatibility spike

Build a separate branch/sample that uses a pinned package version and does not modify the production playback path. Verify:

- flutter pub get, flutter analyze, flutter test, and flutter build apk --release with the project's Flutter 3.35.7 CI toolchain.
- Local MP3, WAV, FLAC, OGG/Opus, AAC/M4A decoding; specifically test actual MP4 video-container files separately rather than assuming every .mp4 is audio.
- Play/pause/resume, seek, next/previous, end-of-track, rapid track switching, and disposal.
- EQ response, bass-boost headroom/clipping, limiter behavior, and stereo widening on speaker, wired headset, and Bluetooth.
- App lifecycle, audio focus/interruption, background playback expectations, and no crash on target Android devices.
- License notices for all bundled native components.

### Phase C — switch only after acceptance

Create a playback adapter that isolates the UI from the engine. Switch to the new engine only when the compatibility spike passes. Keep the existing backend available until regression tests pass on real devices.
